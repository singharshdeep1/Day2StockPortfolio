# Portfolio Trade Order Compliance & Execution Checker

## 1. Project Overview

This application checks proposed portfolio trades before execution. Each
trade is evaluated against compliance and execution-readiness rules and
receives one of three decisions:

-   **Approved** --- all applicable checks pass.
-   **Rejected** --- the trade fails a validation, restriction,
    holdings, or cash check.
-   **Needs Manual Sign-off** --- a buy order exceeds the portfolio's
    maximum position concentration.

The application reads proposed trades from a CSV file and writes each
decision and its reason to an output CSV file.

## 2. Objectives

-   Read proposed trades from a CSV file.
-   Retrieve portfolio reference data using `portfolio_id`.
-   Apply the specified checks in the required order.
-   Produce a decision and reason for every trade.
-   Save the results for review.

## 3. Technology

The project uses Python and its standard library:

  Component                Purpose
  ------------------------ --------------------------------------------
  `csv`                    Read and write CSV files
  `pathlib`                Build paths relative to the project folder
  `decimal.Decimal`        Perform financial calculations
  Dictionaries and lists   Store portfolio reference data

No database, external API, or third-party package is required.

## 4. Project Structure

``` text
portfolio_trade_checker/
├── main.py
├── trade_checker.py
├── portfolio_data.py
├── trades_test.csv
└── trade_results.csv
```

-   **`main.py`** controls the workflow: reads the input file, looks up
    portfolio data, calls the checker, displays decisions, and writes
    the output file.
-   **`trade_checker.py`** contains the validation and compliance
    functions.
-   **`portfolio_data.py`** stores the portfolio reference data.
-   **`trades_test.csv`** contains the proposed trades.
-   **`trade_results.csv`** is generated by the application.

## 5. Input Data

Each trade contains:

  Field             Description
  ----------------- --------------------------
  `portfolio_id`    Identifies the portfolio
  `security_id`     Identifies the security
  `action`          `Buy` or `Sell`
  `quantity`        Number of units to trade
  `price`           Proposed price per unit
  `security_type`   Equity, Bond, or ETF

Portfolio reference data is stored for each portfolio:

  -----------------------------------------------------------------------------
  Field                               Description
  ----------------------------------- -----------------------------------------
  `cash_balance`                      Available cash

  `restricted_securities`             Securities that cannot be traded

  `max_position_pct`                  Maximum permitted concentration,
                                      represented as a fraction (for example,
                                      `0.20` means 20%)

  `current_holdings`                  Holdings represented as
                                      `(security_id, quantity, market_price)`
                                      triples
  -----------------------------------------------------------------------------

The CSV does not contain the portfolio reference data. For this
Python-only implementation, it is stored in `portfolio_data.py` as
in-memory sample data.

## 6. Trade Evaluation Rules

Each trade is checked in the order below. When a check rejects a trade
or requires manual sign-off, evaluation stops for that trade.

### Step 1 --- Validate trade data

Quantity and price must be positive numbers, and action must be `Buy` or
`Sell`.

If validation fails:

-   **Decision:** Rejected
-   **Reason:** `Invalid trade data.`

### Step 2 --- Check restricted securities

The application checks whether `security_id` appears in the portfolio's
`restricted_securities` list.

If it is restricted:

-   **Decision:** Rejected
-   **Reason:** `Security is restricted for this portfolio.`

### Step 3 --- Check sell holdings

This check applies only to sell orders. The application totals the
current quantity held for the security and compares it with the
requested sell quantity.

The trade passes if available quantity is equal to or greater than the
requested quantity.

If holdings are insufficient:

-   **Decision:** Rejected
-   **Reason:** `Insufficient holdings to sell.`

### Step 4 --- Check buy affordability

This check applies only to buy orders.

``` text
trade_cost = quantity × price
```

The order is affordable when `trade_cost` is less than or equal to
`cash_balance`.

If the cost exceeds available cash:

-   **Decision:** Rejected
-   **Reason:** `Insufficient cash for this buy order.`

### Step 5 --- Check position concentration

This check applies only to buy orders that pass the previous checks.

1.  Calculate remaining cash:

    ``` text
    post_trade_cash = cash_balance - (quantity × price)
    ```

2.  Add the proposed quantity to the existing quantity of the security:

    ``` text
    post_trade_quantity = existing_quantity + quantity
    ```

3.  Calculate the post-trade value of that security using the proposed
    trade price:

    ``` text
    post_trade_value_of_this_security = post_trade_quantity × price
    ```

4.  Calculate the value of every other holding using its own stored
    market price. Exclude the security being purchased:

    ``` text
    value_of_other_holdings = sum(quantity × market_price)
    ```

5.  Calculate total portfolio value after the trade:

    ``` text
    total_portfolio_value_after =
        post_trade_cash
        + post_trade_value_of_this_security
        + value_of_other_holdings
    ```

6.  Calculate the position percentage:

    ``` text
    position_pct =
        post_trade_value_of_this_security / total_portfolio_value_after
    ```

If `position_pct` is strictly greater than `max_position_pct`:

-   **Decision:** Needs Manual Sign-off
-   **Reason:**
    `Exceeds maximum position concentration — requires approval.`

A value exactly equal to the maximum is allowed.

### Step 6 --- Approve the trade

If the trade passes all applicable checks:

-   **Decision:** Approved
-   **Reason:** `All compliance and execution-readiness checks passed.`

Sell orders do not undergo the concentration check.

## 7. Application Workflow

1.  `main.py` locates and opens `trades_test.csv`.
2.  `csv.DictReader` reads each row as a dictionary.
3.  The application looks up portfolio reference data using
    `portfolio_id`.
4.  If the portfolio is not found, the trade is rejected with the reason
    `Portfolio reference data not found.`
5.  If the portfolio exists, `evaluate_trade()` in `trade_checker.py`
    applies the rules in order.
6.  The original trade fields are combined with the decision and reason.
7.  `csv.DictWriter` writes the processed trades to `trade_results.csv`.
8.  The application prints a summary in the terminal.

## 8. Output

The output CSV retains the original trade fields and adds:

  Field        Description
  ------------ ----------------------------------------------
  `decision`   Approved, Rejected, or Needs Manual Sign-off
  `reason`     Explanation for the decision

Each input trade produces one output row, including rejected trades.

## 9. How to Run

1.  Install Python if it is not already installed.

2.  Keep `main.py`, `trade_checker.py`, `portfolio_data.py`, and
    `trades_test.csv` in the same folder.

3.  Open a terminal in that folder.

4.  Run:

    ``` bash
    python main.py
    ```

5.  Review the terminal output and open `trade_results.csv`.

## 10. Design Decisions and Assumptions

-   **In-memory reference data:** Portfolio information is stored in a
    Python dictionary because this implementation does not use a
    database or external service.
-   **Sample values:** Portfolio balances, holdings, restrictions, and
    limits in `portfolio_data.py` are sample assumptions unless actual
    reference data is supplied. Decisions based on sample data are
    illustrative, not official approvals.
-   **Financial precision:** `Decimal` is used for financial
    calculations instead of binary floating-point values.
-   **Independent evaluation:** Each trade is evaluated against the
    original portfolio reference data. Cash and holdings are not updated
    after each processed trade. Multiple trades for the same portfolio
    are therefore not treated as a cumulative sequence.
-   **Security type:** `security_type` is retained in the input and
    output, but the assignment does not define a rule that uses it to
    change the decision.
-   **Missing portfolio:** If a `portfolio_id` is not found in the
    reference data, the trade is rejected with a clear reason.

## 11. Possible Future Improvements

-   Validate portfolio reference data before processing trades.
-   Support cumulative trade processing if required by the business

-   Add logging and clearer handling for missing or malformed input

## 12. Conclusion

This project provides a lightweight Python process for checking proposed
portfolio trades before execution. It separates the application workflow
from the compliance logic, applies the specified rules in order, and
records a decision and reason for every trade. It uses only Python's
standard library and can be extended as requirements grow.
